## 소개

저는 서버 개발에서 가장 중요한 가치를 정합성과 안정성으로 보고, 눈에 보이지 않는 결함까지 파고들어 해결하는 백엔드 개발자입니다. 공동구매 플랫폼의 참여·결제 정합성 문제, 이커머스 플랫폼의 조회 성능 개선 등을 직접 해결해오며 이런 태도를 고수했습니다.

문제를 마주하면 겉으로 드러난 증상보다 원인이 되는 구조를 먼저 파악하려고 합니다. 임시방편으로 막기보다 상태나 흐름 자체를 다시 설계해서, 같은 유형의 문제가 재발하지 않도록 만드는 것을 중요하게 생각합니다. 그리고 혼자 해결하고 끝내는 것이 아니라, 왜 그렇게 설계했는지 문서와 코드로 남겨서 팀원 누구든 맥락을 이해하고 이어서 작업할 수 있게 하는 것도 제 역할이라고 생각합니다.

협업할 때는 의견이 다를 때 먼저 근거와 데이터를 가지고 대화하려고 합니다. 제 판단이 항상 맞다고 생각하지 않기 때문에, 팀원의 피드백을 듣고 더 나은 방향이면 기꺼이 수정합니다. 반대로 제가 발견한 구조적인 문제는 명확한 근거를 가지고 팀에 공유해, 프로젝트 전체의 안정성을 함께 높이는 방향으로 움직이려고 합니다. 이런 자세로 앞으로도 안정적이고 신뢰할 수 있는 서비스를 만드는 백엔드 개발자로 성장하고 싶습니다.

**주요 작업**

- **결제 미완료 상태 유령 참여자 차단 및 예약 만료 정책 도입**
  - 참여 API가 결제 상태를 검증하지 않아 정원만 점유한 유령 참여자가 발생, 참여·결제 시점 분리가 원인.
  - 참가 시 자리는 즉시 반영하되 10분 안에 결제(PAID)가 확정되지 않으면 스케줄러가 자동으로 참여를 취소하는 "예약 후 유예" 모델 도입.
  - 결제 페이지 취소·상품 상세 참여취소 버튼도 동일한 취소 로직을 재사용하도록 연결, `TeamReservationExpiryServiceTest` 등 신규 테스트 9건 포함 전체 회귀 테스트 통과 확인.
  - 정원 슬롯이 결제 의사 없는 참여자에게 묶이지 않고 실제 구매자에게 돌아가도록 개선.

- **마지막 참여자 이탈 시 좀비 팀 자동 FAILED 전환**
  - 마지막 1명 남은 참여자는 참여 취소가 막혀 있던 이전 설계(사용자 지적으로 재검토 필요성 발견).
  - 취소 시 팀 상태가 FAILED로 자동 전환되도록 가드를 제거하고 이전 동작을 복원, `TeamControllerTest`에 회귀 케이스 추가.
  - `buyer-mypage.js`가 FAILED 상태를 무조건 "환불 처리됨"으로 표시하던 것도 함께 수정 — 자동환불 설정이 꺼져 있으면 실제로는 승인 대기 상태일 수 있어 라벨이 상태를 단정하지 않게 조정.
  - `TeamConcurrencyTest` 등 인접 테스트 회귀 없음을 확인.

- **가격 구간(PriceTier) 서버 검증 및 maxParticipants 자동 파생**
  - 판매자가 자유 입력하는 정원(maxParticipants)과 가격 구간(PriceTier.minCount)이 따로 검증되지 않아, 정원-가격 조합이 모순될 수 있는 구조 발견.
  - 정원을 사용자가 직접 입력하지 않고 가격 구간 중 최상위 minCount로 자동 파생(SSOT)하도록 변경, 입력 폼은 readonly로 전환.
  - 서비스 레이어에 정가 초과·인원별 가격 역전·구간 중복 검증 추가, `ProductServiceTest`에 역전/중복/파생 회귀 케이스 추가.
  - `seller-product-new.js` / `seller-product-edit.js`에도 동일 검증 적용해 서버 왕복 없이 즉시 피드백.

- **회원·상품·주문·공구팀 표시용 식별자 코드 체계 도입**
  - URL·API 응답에 DB PK가 그대로 노출되는 것을 우려해, 외부 표시용 식별자 코드 도입을 검토.
  - 회원·상품·주문·공구팀 4개 엔티티에 `identifierCode` 컬럼(M-, P-, O-, T- 접두)을 추가하고 신규 데이터 자동 채번 + 기존 데이터 백필 배치 구현.
  - `productCode`는 공개 상품 API에, `teamNo`는 상품 상세·마이페이지에 우선 노출; 기존 PK는 하위 호환을 위해 그대로 유지.
  - admin 노출과 PK 완전 대체(NOT NULL·UNIQUE 제약 포함)는 범위를 좁혀 후속 작업으로 남겨둔 1단계 작업.

### 이커머스 플랫폼
**2026.06 ~ 2026.07 (2개월)**

상품 조회, 장바구니, 주문, 문의, 실시간 상담, AI 챗봇을 제공하는 Spring Boot 기반 이커머스 API 서버. 팀 5명, 인기검색어·인기상품 캐싱 담당 (양지원-실시간 통신/인증인가, 한예진-관리자 주문 인덱싱, 박송이-동시성 제어, 민병준-상품 목록 인덱싱).

**기술 스택**: Java 17, Spring Boot 4.1.0, Spring MVC, Spring Data JPA, Spring Security, Spring WebSocket(STOMP), Spring Cache, Redis, Spring AI(OpenAI), Querydsl 5.0.0, MySQL, H2, JWT(JJWT), Gradle

**주요 작업**

- **반복 조회되는 인기 상품·인기 검색어 매 요청 DB 집계 비용 문제**
  - 인기 상품, 인기 검색어는 반복 조회가 많은 데이터임에도 매 요청마다 DB에서 집계·정렬을 수행해 조회 비용이 큰 구조였음.
  - Redis 기반 글로벌 캐시를 도입해 다중 WAS 인스턴스가 캐시를 공유하도록 설계, 단일 key로 인기 상품/검색어 데이터를 관리.
  - 인기 상품 조회 응답 시간 773.5ms → 3.5ms, 인기 검색어 조회 응답 시간 74.9ms → 3.8ms로 단축, DB 부하 대폭 절감.

- **캐시 만료 시점 트래픽 몰림 및 Redis 장애 대응**
  - 캐시가 만료되는 시점에 요청이 몰리면 DB로 트래픽이 튀는 문제를 막기 위해, 스케줄러 기반 캐시 warm-up 로직을 도입해 캐시를 주기적으로 미리 갱신.
  - 코드 리뷰에서 Redis 장애 시 캐시 의존적으로 서비스가 통째로 중단될 수 있는 단일 장애점을 지적받아, 캐시 조회 실패 시 DB 조회로 자동 전환되는 fallback 로직을 추가해 제거.
